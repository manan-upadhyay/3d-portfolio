### §7b — JS budget: the answer

**Will ~231 KB gz (index + react + animation vendors; ~304 KB with the
analytics vendor) affect performance?** Modestly, and only on first visit. As a
React SPA the first paint waits on the eager JS, so it is part of LCP — but the
heavy levers were already pulled (esnext output, CSS inlined into the HTML,
images −9.7 MB, sections/voices/Atelier lazy). On a mid-range phone over 4G
this is roughly 1–1.5 s of download+parse; on desktop it is negligible; repeat
visits are cached. It will not degrade scrolling or runtime FPS — it is a
one-time cost.

**Can anything be done without cutting content, animations, or assets?** One
real lever: **defer PostHog**. `posthog-js` (73 KB gz + a measured ~106 ms init
long task) is imported statically in `main.jsx` but consumed *only* through the
`lib/analytics.js` façade — so it can be dynamic-imported on idle/first
interaction with a small event-buffer in the façade, taking it off the critical
path entirely. Trade-off: visitors who bounce inside ~1 s may not register a
pageview (mitigate with a short idle timeout). Everything else (GSAP, Framer,
Lenis, React) is genuinely needed at first paint for the hero moment — leave
it. The CLAUDE.md "<~200 KB gz" line should be restated to match reality
(~230 KB eager + analytics async if the defer ships; ~305 KB as-is), which is a
conscious, documented budget rather than a silent breach.
